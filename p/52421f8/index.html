Constructor.java:495

其实到这里已经真相大白了

通过这三行堆栈，可以推断出 checkAccess 是 true，而 checkAccess = !override，说明在异常出现的时候，override 是 false。

但是在本地环境正常 debug 的话，这里的 override 是 true 的。

fastjson 反序列化时遇到 package-private 的类应该是会通过反射，需要设置 setAccessible 为 true 才能访问 package-private 的对象，进而创建对象。

回过头看反序列化器的构建过程，来找是哪里出现了问题，导致 setAccessible 未设置为 true。

com.alibaba.fastjson.parser.ParserConfig#createJavaBeanDeserializer(ParserConfig:935)，在方法中判断是否适用 ASM 进行反序列化。

  • 如果不支持 ASM，那么将通过反射进行类的生成。

  • 如果支持将通过 asmFactory.createJavaBeanDeserializer 生成一个 ASM 的反序列化器。

在构建 beanInfo 的时候，com.alibaba.fastjson.util.JavaBeanInfo.java:579

这里通过 TypeUtil 设置 override 为 true，跳过 checkAccess，get/set/invoke/newInstance 可以直接执行。

接下来就是确认 TypeUtils 中的 setAccessibleEnable 的值，通过 arthas：

  1. 安装

  2. 查看类加载器的 hash， 最后一行拿到 classLoaderHash 3874b815

  3. 查看变量值，发现是 @Boolean[false]

这里可以看到机器上当前环境的 fastjson 中 setAccessibleEnable 被某次异常修改成 false。fastjson 自身的防御机制过于激进，一次 setAccessible 失败就永久关闭全局开关。

想要复现测试，可以通过反射把全局开关置为 false（模拟被污染的进程状态）
